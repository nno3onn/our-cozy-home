# 우리집 결정 기록

최종 수정일: 2026-10-07

제품 명세가 정하지 않은 되돌리기 쉬운 기본값과 선택 이유를 기록한다. 제품 규칙을
바꾸는 결정은 이 문서만 수정하지 않고 `product-spec.md`도 함께 갱신한다.

## D-033 토스식 UI Foundation의 단계적 전환

- 상태: 채택
- 결정: 제품 UI는 neutral semantic token과 Pretendard Variable을 기본으로 사용한다.
  주요 행동은 `#3182F6`, 페이지 배경은 `#F7F8FA`, 기본 본문은 `#191F28`로 통일한다.
  방·동물·가구의 따뜻한 asset 색은 scene 영역에 유지한다. 기존 `cream`·`ink` 등의 token과
  `heading`·`quiet` API는 개별 화면 전환이 끝날 때까지만 compatibility alias로 유지한다.
- 이유: 모든 화면을 한 번에 재작성해 Demo Mode와 실제 서버 흐름을 깨뜨리지 않으면서도,
  후속 화면이 같은 정보 계층과 접근성 계약으로 이동할 수 있게 하기 위해서다.
- 비용: Foundation 병합 직후에는 새 primitive와 legacy 화면이 함께 존재한다. alias 제거는
  전체 route 전환과 viewport 회귀 검증이 끝난 별도 Issue에서 수행한다. 첫 버전은 light theme로
  고정하되 semantic 이름은 향후 theme 확장을 막지 않게 한다.

## D-001 저장소와 패키지 관리

- 상태: 채택
- 결정: 단일 Expo 앱과 `supabase` 디렉터리를 한 저장소에 둔다. 패키지 관리자는
  npm을 사용하고 잠금 파일을 커밋한다.
- 이유: 첫 버전에 별도 서버가 없고 Expo 기본 도구와 가장 단순하게 호환된다.

## D-002 실행 모드 선택

- 상태: 채택
- 결정: `EXPO_PUBLIC_APP_MODE=demo|supabase`를 명시적으로 선택한다. 값 또는 실제
  모드 환경 변수가 잘못되면 설정 오류를 보여주고 자동으로 데모로 전환하지 않는다.
- 이유: 목업 동작을 실제 연동 성공으로 오인하지 않게 한다.

## D-003 데모 상태 저장

- 상태: 채택
- 결정: 첫 구현은 메모리 기반 데모 repository를 사용하고 데모 전용 초기화 명령을
  제공한다. 앱 재시작 뒤 영구 보존은 보장하지 않는다.
- 이유: 인증 정보 없이 모든 핵심 화면을 재현하면서 실제 데이터 계층과 분리한다.

## D-004 방 좌표와 배치

- 상태: 채택
- 결정: `1000 x 1000` 논리 좌표와 카테고리별 고정 슬롯을 사용한다. 드래그는
  자유 좌표가 아니라 가장 가까운 호환 슬롯을 선택한다.
- 이유: 화면 크기 차이를 흡수하고 첫 버전의 충돌·동기화 복잡도를 제한한다.

## D-005 추억 글 수정 이력

- 상태: 채택
- 결정: 기여 글은 revision을 추가하며 viewer의 퇴장 시각 이전 마지막 revision을
  조회한다. 원본 삭제는 revision 시점과 무관하게 모든 접근을 차단한다.
- 이유: 탈퇴 당시 공개 범위를 유지하면서 원작자 삭제 정책을 일관되게 적용한다.

## D-006 계정 삭제와 공동 추억

- 상태: 채택
- 결정: 계정 삭제 시 본인의 공동 기여 글·사진은 삭제하고 작성자 정보를
  비식별화한다. 다른 사용자의 기여와 이미 확정된 추억 가구는 유지한다.
- 이유: 본인 콘텐츠 정리 요청과 공동 결과의 타 사용자 소유권을 함께 보존한다.

## D-026 계정 삭제의 참조 보존 tombstone

- 상태: 채택
- 결정: Auth 사용자는 Edge Function으로 물리 삭제하되, `profiles`와 `animals`는
  식별 정보를 제거한 tombstone으로 남긴다. 공동 추억·완성 가구·습득 버릇이 참조하는
  과거 ID를 깨지 않으면서 UI에는 `떠난 친구`·`떠난 동물`만 표시한다.
- 이유: 다른 사용자의 공동 결과를 삭제하지 않고 Auth 삭제를 재시도 가능하게 한다.

## D-007 사진 업로드 제한

- 상태: 채택
- 결정: JPEG, PNG, HEIC/HEIF 원본 10MB 이하만 받고 긴 변 2048px, JPEG 품질
  0.82로 압축한다. 결과가 5MB를 넘으면 업로드하지 않는다.
- 이유: 모바일 품질을 유지하면서 Storage와 전송 비용을 제한한다.

## D-008 에셋 완성 상태

- 상태: 채택
- 결정: 카탈로그에 `placeholder|final` 상태를 둔다. 동물 두 종과 가구 한 테마로
  방 스타일을 먼저 검증하고 나머지 항목은 그 전까지 placeholder로 표시한다.
- 이유: 55개 외형의 양보다 시점·비율·윤곽선의 일관성을 먼저 확정한다.

## D-009 불확실한 구매 응답

- 상태: 채택
- 결정: 구매 응답이 끊기면 같은 멱등 키의 결과 조회 RPC로 조정한 후 결과가 없을
  때만 같은 키로 재시도한다.
- 이유: 네트워크 실패와 서버 처리 실패를 구분해 이중 차감·지급을 막는다.

## D-010 구현 단위

- 상태: 채택
- 결정: 화면 전체, 서버 전체 순서가 아니라 집, 경제, 추억처럼 기능별로 화면,
  repository, RPC, RLS, 오류와 테스트를 연결해 완성한다.
- 이유: 각 단계가 실행 가능하며 실제 사용자 흐름의 누락을 조기에 발견할 수 있다.

## D-011 실제 계정 삭제 실행자

- 상태: 채택
- 결정: 앱 데이터 정리는 멱등한 삭제 요청으로 기록하고 Supabase Auth 사용자 삭제는
  service role을 가진 Edge Function이 마지막에 수행한다.
- 이유: service role key를 앱에 포함하지 않고 부분 실패를 안전하게 재시도한다.

## D-012 파일럿 방의 시각 구조

- 상태: 채택
- 색상: 종이 크림 `#FFF8E8`, 바닥 모래 `#F0DFC0`, 먹색 `#38332E`, 복숭아
  `#F2A98C`, 민트 `#91C9AF`, 하늘 `#94BFE0`을 사용한다.
- 글꼴: 작은 화면의 한국어 가독성과 네이티브 일관성을 위해 플랫폼 산세리프를
  사용하고 크기·굵기·행간으로 위계를 만든다.
- 배치: 방을 종이 인형극 무대처럼 화면의 대부분에 두고, 정보는 상단의 얇은
  집 이름·인원 띠와 하단의 하나뿐인 행동 패널에 모은다.

```text
┌ 우리집 이름                         4/4 ┐
│                                            │
│            벽과 창, 교체 가구             │
│       동물+이름표       동물+이름표        │
│          러그와 탁자, 식물                 │
│       동물+이름표       동물+이름표        │
├ 선택한 동물 상태와 먹기·쉬기·놀기 버튼 ───┤
└ 우리집          꾸미기          추억       ┘
```

- 원칙: 기억에 남는 요소는 동일한 둥근 카드 묶음이 아니라 네 동물이 함께 있는
  방 무대다. 이름표는 사용자 색의 작은 천 라벨처럼 보이되 색만으로 구분하지 않는다.
  그림자는 모두 오른쪽 아래 한 방향이고 패널은 동물의 얼굴과 주요 가구를 가리지
  않는다.
- 검토: 크림+테라코타 중심의 흔한 랜딩 페이지 인상을 피하려고 갈색 대비를 줄이고
  민트·하늘색을 주요 상호작용 색으로 옮겼다. 불필요한 그라데이션, 다수의 둥근 카드,
  장식용 영문 라벨과 자동 등장 애니메이션은 사용하지 않는다.

## D-013 placeholder 에셋 표현

- 상태: 채택
- 결정: 첫 실행 버전은 투명 비트맵을 가장한 파일을 대량 생성하지 않고 Skia와 React
  Native 도형으로 placeholder를 그린다. 카탈로그의 `thumbnailKey`, `roomAssetKey`,
  `assetStatus`는 최종 에셋 교체 지점을 유지한다.
- 이유: 배경 사각형과 해상도 문제 없이 55종의 데이터 완전성을 먼저 확인하고, 최종
  이미지가 준비됐다고 잘못 보고하지 않기 위해서다.

## D-014 데모 방의 꾸미기 범위

- 상태: 채택
- 결정: 자유 드래그 대신 `floor-accent-left` 고정 슬롯에서 호환 가구를 교체한다.
  선택은 Zustand, 소유권·배치·버전은 repository가 관리한다.
- 이유: 실제 서버의 낙관적 배치 버전 계약을 유지하면서 첫 방 화면에서 교체 흐름을
  완결하기 위해서다.

## D-015 웹 방 렌더링

- 상태: 채택
- 결정: iOS·Android 방은 Skia를 사용하고, 웹은 같은 논리 좌표·터치 계약을 따르는
  React Native View 도형 렌더러를 사용한다.
- 이유: 웹을 정식 실행 대상으로 제공하면서 CanvasKit 초기화 실패를 피하고, 웹 검증을
  네이티브 Skia 검증으로 잘못 간주하지 않기 위해서다.

## D-016 원격 Supabase 우선 연결

- 상태: 채택
- 결정: 로컬 Docker daemon을 사용할 수 없는 개발 환경에서는 서울 리전 원격 Supabase
  프로젝트를 앱·통합 검증의 우선 대상으로 사용한다. 로컬 CLI 설정과 migration 파일은
  계속 유지하며, Docker가 제공되는 환경에서의 local reset·SQL test는 별도 검증으로
  남긴다.
- 이유: 실제 Auth·RLS·Storage·동시성 검증을 Docker 설치에 막히지 않고 진행하되,
  로컬 재현 가능성 자체를 포기하지 않기 위해서다.

## D-017 원격 schema 적용 이력

- 상태: 채택
- 결정: DB 비밀번호 없이 원격 기반 schema를 검증해야 하는 동안에는 Dashboard SQL
  Editor로 추가 전용 migration의 동일 SQL을 적용한다. migration은 안전하게 재실행할 수
  있도록 idempotent guard를 갖추고, DB 비밀번호를 준비한 뒤에는 `supabase link`와
  migration history 정합 확인을 선행한다.
- 이유: 실제 RLS·생성 타입 검증을 진행하면서 DB 비밀번호를 저장소·앱에 노출하지 않기
  위해서다.
- 비용: 적용 이력 정합 전에는 원격 배포를 실행하지 않는다. 정합을 확인한 뒤에도
  수동 확인값과 repository secret을 요구하는 CI workflow만 사용할 수 있다.

## D-018 온보딩 완료 기준

- 상태: 채택
- 결정: Supabase 사용자는 자기 `profiles` 행과 한 마리의 `animals` 행이 모두
  있을 때에만 온보딩 완료로 판단한다. 둘 중 하나가 없거나 조회가 실패하면 홈
  화면으로 진행하지 않는다.
- 이유: 사용자 소유 동물이 없는 상태로 집·추억·버릇 흐름에 진입하는 것을 막고,
  네트워크 실패를 신규 사용자로 잘못 해석하지 않기 위해서다.

## D-019 집 생성 요청 키

- 상태: 채택
- 결정: 집 생성 화면은 사용자 입력이 유지되는 동안 하나의 request key를 재사용한다.
  `crypto.randomUUID()`를 우선 사용하고, 지원하지 않는 환경에서는 시간·난수 조합을
  사용한다.
- 이유: 응답이 끊긴 뒤 사용자가 다시 누르는 경우 서버가 같은 집·멤버십 결과를
  반환하게 하며, 별도 UUID 의존성을 추가하지 않기 위해서다.

## D-020 초대 링크 표시와 로그인 복귀

- 상태: 채택
- 결정: 초대 원문 토큰은 생성 RPC의 단일 응답에서만 받고, 집장 화면의 컴포넌트
  상태와 로그인 직전의 Auth 메모리 상태에만 유지한다. 링크를 본 비로그인 사용자는
  로그인·온보딩을 마친 뒤 같은 초대 미리보기로 돌아간다. 링크 공유는 운영체제의
  URL 생성 계약(`expo-linking`)을 사용한다.
- 이유: 초대 링크가 자리 예약이나 입주 성공처럼 보이지 않게 하면서, 로그인 중
  링크 문맥이 사라지는 문제를 막는다. 토큰을 전역 로그, 서버 조회 캐시 또는
  영구 저장소에 보관하지 않아 노출 범위를 줄인다.

## D-021 초대 수락 요청 키

- 상태: 채택
- 결정: 초대 수락 버튼은 화면 수명 동안 하나의 요청 키를 재사용한다. 서버는
  `(profile_id, request_key)` 결과를 기록해 같은 키의 재전송에 기존 membership을
  반환한다.
- 이유: 모바일 네트워크에서 응답만 유실된 경우에 중복 membership·수락 이력을 만들지
  않고, 사용자가 수락 결과를 안전하게 복구할 수 있다.

## D-022 오프라인 확정 명령 차단

- 상태: 채택
- 결정: 마지막 성공 query 결과는 읽기 전용으로 남기되, Supabase repository 앞의
  연결 가드가 모든 서버 확정 명령을 거부한다. 화면도 출석·입주·구매·배치·동물 행동을
  비활성화하고 `오프라인 읽기 전용`을 명시한다. 자동 offline queue나 재생은 만들지
  않는다.
- 이유: 버튼 비활성화만으로는 네트워크 전환과 재시도에서 중복 실행을 막을 수 없고,
  캐시된 집 정보가 현재 권한을 증명하지 않기 때문이다.
- 비용: 현재 감지는 웹 browser event에 기반한다. 네이티브 reachability는 실제 기기
  검증과 함께 보강해야 하며, 이 단계에서 완료로 주장하지 않는다.

## D-023 Push Outbox 실행자

- 상태: 채택
- 결정: 알림은 DB outbox event → 수신자 delivery → Expo token target으로 기록하고,
  Edge Function은 worker secret을 가진 scheduler만 호출한다.
- 이유: 성공한 게임 규칙 트랜잭션과 알림 발생을 분리하지 않으면서도 여러 기기 token,
  Expo receipt, 재시도 및 탈퇴 직전 권한 재검증을 안전하게 처리할 수 있다.
- 비용: scheduler와 `NOTIFICATION_WORKER_SECRET`은 프로젝트 운영 설정이므로 저장소가
  자동 생성하지 않는다. 원격 배포와 실제 기기 검증을 별도로 기록해야 한다.

## D-027 게임형 우리집 셸과 스크랩북 표현

- 상태: 채택

  방 무대와 접근 가능한 게임형 탐색 버튼을 제공한다. 서버 snapshot은 TanStack Query가
  계속 소유하고, 셸의 Zustand 상태에는 선택 동물·열린 패널처럼 일시적인 UI만 둔다.
  추억은 공동 앨범과 탈퇴 뒤 개인 보관함을 분리한 월별 스크랩북 카드로 표시한다.
- 이유: 앱의 중심을 목록형 관리 화면이 아니라 친구 동물이 함께 있는 방으로 유지하면서,
  기존 권한·소유권·오프라인 읽기 전용 계약을 바꾸지 않기 위해서다.
- 비용: 추억 가구 완성 축하는 현재 contribution RPC가 이번 요청의 가구 생성 여부와
  owned item ID를 반환하지 않아 presentation 컴포넌트만 준비했다. RPC contract 확장 전에는
  임의의 완료 모달이나 방 배치를 만들지 않는다.

## D-028 일러스트 파일의 단계적 적용

  카탈로그 항목은 같은 `thumbnailKey`/`roomAssetKey` manifest 계약을 통해 placeholder로

- 이유: 한 테마의 실제 방 화면으로 시점·윤곽·그림자 방향을 먼저 검증하면서, 55개

- 비용: 현재 파일럿 밖의 상점·추억 가구는 최종 제작 에셋이 아니며, 제작 완료 전까지
  placeholder가 보이는 것이 의도된 상태다.

## D-029 반응형 레이아웃 계약

- 상태: 채택
- 결정: 화면 폭 600px 미만은 한 열과 하단 탐색/트레이, 600–899px는 두 열과 하단
  탐색/트레이, 900px 이상은 최대 3열(에셋 목록은 4열)과 데스크톱 탐색 레일/꾸미기
  보조 패널을 사용한다. 목록 카드의 최소 폭은 156pt(에셋 목록 180pt)이며, 읽기·작성
  화면은 640–760pt의 중앙 열을 넘지 않는다.
- 이유: 모바일에서 방과 주요 CTA의 손 닿는 위치를 보존하면서 태블릿·데스크톱에서는
  가로 공간을 목록 밀도에만 사용해 내용을 과도하게 넓히지 않기 위해서다.
- 비용: 브라우저 창 크기 변경은 화면 구성만 바꾸고 저장된 방 좌표·가구 배치·서버
  데이터에는 영향을 주지 않는다. 실제 iOS/Android 키보드·스크린리더 검증은 별도다.
- 방 배경·동물·가구는 동일한 정사각형 장면 컨테이너를 기준으로 확대·축소한다. 특히 웹의
  방 배경은 원본 이미지의 고유 크기에 맡기지 않고 장면의 `width`·`height` 100%로 먼저
  제한한 뒤 `cover`를 적용한다. 이 계약으로 viewport가 좁아져도 배경만 잘리고 오브젝트가
  원래 좌표에 남는 현상을 막는다.
- 배경 원화에 이미 포함된 큰 러그와 창가 화분은 기본 방 장식으로 취급해 같은 스프라이트를 다시
  겹치지 않는다. 동물과
  추억 가구의 시각 크기에는 최소 픽셀값을 강제하지 않고 장면 비율을 그대로 적용하되, 터치
  영역은 별도의 44pt 접근성 계약으로 유지한다.

## D-030 원격 migration의 수동 CI 실행

- 상태: 채택
- 결정: 원격 Supabase migration 적용은 고정 프로젝트 ref를 사용하는
  `workflow_dispatch` GitHub Actions에서만 실행한다. 확인 문자열과
  `SUPABASE_ACCESS_TOKEN`·`SUPABASE_DB_PASSWORD` repository secret이 모두 있어야 하며,
  push·PR로 자동 실행하지 않는다.
- 이유: 현재 개발 환경의 IPv6 직접 DB 경로에 의존하지 않으면서, DB password와 personal
  access token을 로컬 `.env`·앱 번들·workflow log에 노출하지 않고 재현 가능한 적용 경로를
  만들기 위해서다.
- 비용: workflow source를 추가한 것만으로 원격 schema가 적용되지는 않는다. 관리자가
  secrets 설정과 명시적 dispatch를 완료한 뒤, 실제 migration history와 다계정 E2E를 따로
  확인해야 한다.

## D-031 미니어처 인형·가구 에셋 톤

- 상태: 채택
- 결정: 동물은 둥근 봉제 인형/펠트 질감의 소형 collectible, 가구와 방은 따뜻한 옅은 목재와
  크림·파우더 블루를 쓰는 미니어처 dollhouse 제품으로 표현한다. 방 배경의 중앙 바닥은 네
  동물과 배치 가구를 위한 비어 있는 무대로 유지한다. 모든 신규 에셋은 아이소메트릭에 가까운
  3/4 시점, 단일 명확한 기능, 제한된 소품과 단순한 실루엣을 지킨다. 이름·개인 포인트 색상은
  PNG 안이 아니라 UI에서 제공한다.
- 이유: 과한 장식·광택·서사적 소품이 섞인 생성형 일러스트 인상을 피하고, 실제 작은
  방 모형처럼 일관된 스케일·재질·가독성을 유지하기 위해서다.
- 비용: 털·목재 표현은 촉감만 전달하는 수준으로 제한하며, 개별 에셋의 스타일 변형은
  먼저 파일럿 방 화면에서 확인한 뒤 확대한다.
  현재 상점 파일럿은 낮은 봉제 쿠션, 옅은 목재 탁자, 무광 점토 화분까지 같은 기준으로
  교체했으며, 나머지 placeholder를 최종 에셋으로 대체할 때도 이 기준을 따른다.
  두 번째 세트부터는 한 종류 안에서도 색만 바꾸지 않고 구름 발란스·튤립 받침·매듭·물결·
  통나무처럼 실루엣과 재료 구성을 함께 바꾼다. 생성 원본에 이미 투명 채널이 있으면 추가
  배경 제거로 가장자리를 훼손하지 않고 알파 PNG를 그대로 사용한다.
  세 번째 세트도 잎 자수 패널·구름형 저상 탁자·직조 데이지 러그·별 봉제 쿠션처럼 같은
  카테고리 안에서 형태와 촉감을 함께 바꾸며, 추억 가구의 사진 영역은 실제 비공개 내용을
  에셋에 합성하지 않고 중립 placeholder 면으로 둔다.
  네 번째 세트는 가구 하나의 기능과 실루엣이 작은 화면에서도 먼저 읽히도록 제한했다.
  초기 딸기 캐노피와 별밤 식탁 시안처럼 장식 소품이 장면을 이루는 결과는 사용하지 않고,
  소품을 덜어낸 단일 제품형 시안을 다시 제작해 채택한다.
  다섯 번째 세트는 상점의 남은 9종을 모두 완성하며, 바닥 가구는 낮은 3/4 시점, 커튼은
  정면, 간식은 접시를 포함한 단일 제품 구도로 고정했다. 브런치 식탁은 비공개 추억 내용을
  이미지에 넣지 않고 빈 식기만 둔다.
  마지막 세트는 눈꽃 식탁·카세트 라디오·조개 라디오와 구름·별·우표 액자를 같은 제품형
  구도로 완성한다. 액자 면에는 사진이나 글을 영구 합성하지 않고 중립적인 빈 면만 두며,
  실제 추억 내용은 권한 확인 뒤 별도 UI 계층에서만 표시한다. 이 세트로 v1 카탈로그 55종은
  모두 `final` 에셋을 사용하며 신규 placeholder 항목을 추가하려면 상태를 명시적으로 구분한다.

## D-032 원격 카탈로그는 migration으로 게시

- 상태: 채택
- 결정: v1의 12개 배치 슬롯과 55개 상품 정의를 추가 전용 migration에 스냅샷으로
  저장한다. seed는 로컬 초기화를 위해 유지하지만, 원격 `db push`가 seed를 실행하지
  않는 특성에 의존하지 않는다.
- 이유: 새 개발 환경과 원격 Supabase에서 동일한 상점 목록을 재현하고, 실제
  계정 상점이 빈 화면으로 나오는 것을 막기 위해서다.
- 비용: 후속 카탈로그 변경은 이 스냅샷을 수정하지 않고 새 migration으로
  추가한다.
