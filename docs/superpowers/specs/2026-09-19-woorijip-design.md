# 우리집 모바일 앱 설계 명세

작성일: 2026-09-19

## 1. 제품 목표

우리집은 한 집에 1~4명이 머물며 각자의 동물을 키우고, 방을 꾸미고,
함께한 기록을 추억 가구로 남기는 iOS·Android 모바일 앱이다. 한 사용자는
동시에 하나의 활성 집에만 속한다. 혼자서도 집 생성, 기록, 출석, 구매,
꾸미기를 할 수 있으며 가입자를 다른 집에 자동 배정하지 않는다.

첫 버전의 핵심은 다음과 같다.

- 초대 링크 또는 코드 하나로 빈자리만큼 여러 친구가 입주할 수 있다.
- 집 정원, 소속, 보상, 구매, 추억 완성, 버릇 학습은 서버가 확정한다.
- 서로 다른 두 사람이 기여하면 추억 가구가 정확히 한 번 완성된다.
- 동물 두 마리가 서로 다른 3일 동안 함께 활동하면 버릇을 배운다.
- 각 사용자와 가구의 소유권은 집 소속이 바뀌어도 보존된다.
- Supabase 계정 없이도 명시적인 데모 모드에서 주요 화면과 흐름을 확인한다.

실제 결제, 관리자 강제 퇴장, 자유 좌표 기반 가구 배치, 정밀한 동물 위치
동기화는 첫 버전 범위에 포함하지 않는다.

## 2. 기술 선택

### 2.1 애플리케이션

- Expo와 React Native, TypeScript를 사용한다.
- Expo Router가 인증, 온보딩, 집 진입, 메인 탭, 상세 화면과 딥 링크를
  관리한다.
- 메인 탭은 `우리집`, `꾸미기`, `추억`으로 구성한다.
- 설정과 구성원 관리는 스택 화면으로 연다.
- React Native Skia가 방, 가구, 동물을 기준 좌표계에 그린다.
- Reanimated가 숨쉬기, 뛰기, 고개 기울이기, 등장 효과를 담당한다.
- Gesture Handler가 동물·가구 터치와 꾸미기 드래그 입력을 담당한다.
- Zustand는 선택 상태, 꾸미기 모드, 열린 패널 같은 일시적 UI 상태만
  저장한다.
- TanStack Query는 서버 데이터 조회, 캐시 무효화와 재조회에 사용한다.
- Jest와 React Native Testing Library로 도메인 및 화면 동작을 검증한다.

Supabase CLI가 생성한 데이터베이스 타입은
`src/types/database.generated.ts` 한 곳에 저장한다. 앱의 도메인 타입은 이
생성 타입을 그대로 중복 선언하지 않고 필요한 행·RPC 결과 타입을 조합해 만든다.

패키지는 프로젝트를 생성하는 시점의 안정적인 Expo SDK가 권장하는
호환 버전으로 설치하고 잠금 파일을 커밋한다. Expo 관리 패키지는
`npx expo install`로 설치해 버전 조합을 유지한다.

### 2.2 백엔드

별도 Express 또는 NestJS 서버 없이 Supabase를 사용한다.

- Auth: 회원가입, 로그인, 세션과 사용자 식별
- PostgreSQL: 영구 데이터와 트랜잭션 게임 규칙
- Storage: 비공개 추억 사진
- Realtime: 같은 집의 변경 사실 전달
- Database Functions: 원자성이 필요한 규칙과 권한 검사
- Edge Functions: Expo Push Service 같은 외부 서비스 호출

일반 조회는 RLS가 적용된 테이블을 앱이 직접 읽는다. 여러 행을 함께
변경하거나 경쟁 상태가 발생하는 명령은 `security definer` RPC로 실행한다.
RPC는 `auth.uid()`를 사용하며 앱이 보낸 사용자 ID, 가격, 보상 금액,
관리자 여부를 신뢰하지 않는다. 함수의 `search_path`를 고정하고 허용된
역할에만 실행 권한을 부여한다.

## 3. 저장소 구조

```text
app/                         Expo Router 화면과 레이아웃
src/
  components/                접근 가능한 공통 UI
  features/                  auth, house, room, shop, memories, habits 등
  game/                      Skia 장면, 기준 좌표, 행동·배치 규칙
  repositories/              앱이 의존하는 데이터 접근 인터페이스
    demo/                    로컬 시드 기반 데모 구현
    supabase/                실제 Supabase 구현
  stores/                    Zustand UI 상태
  lib/                       Query, Supabase, 링크, 알림 설정
  types/                     도메인 타입과 생성된 DB 타입
  catalog/                   아이템·행동 카탈로그
assets/                      교체 가능한 동물·가구 에셋
supabase/
  migrations/               스키마, 제약, RLS, RPC, 시드 마이그레이션
  functions/send-push/       Expo 푸시 발송 Edge Function
  tests/                     pgTAP 및 SQL 통합 테스트
docs/                        연동·운영·설계 문서
```

기능은 화면, 훅, 도메인 서비스와 테스트를 가까이 둔다. 화면은 저장소
구현이나 Supabase 클라이언트를 직접 참조하지 않고 기능 훅을 통해 접근한다.

## 4. 실행 모드와 인증

`EXPO_PUBLIC_APP_MODE`는 `demo` 또는 `supabase`만 허용한다. 값이 없거나
Supabase 환경 변수가 빠지면 앱은 자동으로 실서비스처럼 동작하지 않고,
설정 오류 화면에서 데모 모드 진입 방법을 안내한다.

데모 모드는 다음 원칙을 지킨다.

- 화면 상단에 항상 `데모 모드` 표식을 표시한다.
- 고정 사용자 네 명, 동물 네 마리, 집, 아이템, 추억, 학습 데이터를 제공한다.
- 메모리 저장소를 사용하며 실제 인증·푸시·Storage·Realtime 완료를 주장하지
  않는다.
- 서버 경쟁 상태 검증은 데모가 아니라 PostgreSQL 테스트가 담당한다.
- 앱 재시작 시 초기 상태로 돌아갈 수 있음을 설정 화면에 알린다.

Supabase 모드는 이메일 기반 기본 인증 흐름을 제공한다. 로그인 전에 받은
초대 토큰은 민감 정보가 아닌 로컬 pending-link 상태에 잠시 저장하고, 로그인
후 서버에 토큰을 제출해 다시 검증한다. 링크의 집 ID, 인원, 초대자 정보는
권한 판단에 사용하지 않는다.

## 5. 데이터 모델

모든 주요 테이블은 UUID 기본 키와 `created_at`, 필요한 경우 `updated_at`을
가진다. 시간은 `timestamptz`, 게임 날짜는 `Asia/Seoul` 기준 `date`로 저장한다.

### 5.1 사용자, 집과 소속

- `app_settings`: `house_capacity = 4`, 출석 보상 등 서버 공통 설정
- `profiles`: 표시 이름, 개인 포인트 색상, 코인 잔액, 알림 설정
- `houses`: 이름, `active|archived` 상태, 현재 집장 사용자
- `house_memberships`: 사용자, 집, `active|left`, 역할, 가입·탈퇴 시각
- `house_invites`: 집당 활성 토큰/코드 하나, 생성자, 만료·종료 사유
- `invite_acceptances`: 초대, 사용자, 멱등 키, 수락 결과와 시각
- `animals`: 사용자 소유 동물, 종류, 이름, 현재 표현 상태
- `push_tokens`: 사용자별 Expo 토큰, 플랫폼, 유효 상태

활성 멤버십에는 사용자별 부분 고유 인덱스를 두어 한 사용자의 활성 집을
하나로 제한한다. 집당 활성 초대에도 부분 고유 인덱스를 둔다. 정원 4명은
행 단위 제약만으로 표현하지 않고 공통 설정을 읽는 RPC 안에서 집 행을 잠근
뒤 검사한다.

### 5.2 아이템과 방

- `item_definitions`: 카테고리, 테마, 이름, 가격, 소비성 여부, 에셋 키,
  기준점, 크기, 허용 슬롯, 상호작용 메타데이터
- `owned_items`: 소유 사용자, 정의 ID, 출처, 수량, 회수 상태
- `room_slots`: 기준 좌표계의 고정 슬롯, 슬롯 유형과 렌더 순서 보조 정보
- `room_placements`: 집, 슬롯, 소유 아이템, 배치 버전
- `purchase_requests`: 사용자와 멱등 키별 구매 결과
- `attendance_rewards`: 사용자와 한국 날짜별 보상 결과

생활 아이템은 커튼, 탁자, 쿠션, 러그, 침대, 조명, 식물, 간식의 8개
카테고리마다 5종씩 총 40종이다. 추억 가구는 식탁, 라디오, 액자 세 종류마다
5가지 외형으로 총 15종이다. 같은 정의의 아이템도 `owned_items` 행은 구매자별로
분리한다. 공동 지갑은 만들지 않는다.

### 5.3 추억과 접근 권한

- `memories`: 집, 작성자, `private_draft|shared|completed`, 공유 시각,
  완성 시각, 생성된 가구 ID
- `memory_viewers`: 공유 시점의 대상 사용자와 열람·기여 권한 스냅샷
- `memory_contributions`: 추억, 기여 사용자, 본문, 생성·수정 시각
- `memory_photos`: 추억, 기여자, 비공개 Storage 객체 경로와 메타데이터

혼자 만든 첫 기록은 `private_draft`로 보관한다. 작성자가 명시적으로 공유할
때 현재 활성 멤버를 `memory_viewers`에 고정하고 `shared`로 전환한다. 처음부터
공동 추억을 시작하는 경우에도 시작 당시 멤버를 같은 방식으로 고정한다.
후입주자는 과거 추억의 viewer가 되지 않는다.

서로 다른 두 viewer가 기여하면 `completed`가 되고 추억 가구 한 개를 만든다.
동일 사용자의 수정 횟수는 기여자 수를 늘리지 않는다. 세 번째와 네 번째
사용자의 기여는 같은 추억 상세에 추가되며 가구를 다시 만들지 않는다.
완성 가구 생성은 `memories.generated_item_id`의 고유성과 조건부 갱신으로
정확히 한 번만 수행한다.

탈퇴자는 자신이 직접 기여한 추억만 개인 보관함에서 계속 볼 수 있다.
탈퇴 이후 다른 사용자가 새로 추가한 기여와 사진은 볼 수 없고 수정할 수도
없다. 현재 집 멤버 가운데 viewer가 아닌 사람이 있으면 해당 추억 가구는
공동 방 조회에서 제외하고 viewer의 개인 추억 보관함에 유지한다.

### 5.4 버릇 학습

- `habit_definitions`: 버릇 ID, 이름, 표현 행동과 에셋 메타데이터
- `habit_learning`: 배우는 동물, 가르치는 동물, 버릇, 상태, 시작·종료 시각
- `habit_activity_days`: 학습과 한국 게임 날짜의 고유 기록
- `habit_activity_participants`: 해당 날짜에 두 사용자가 참여했음을 증명하는 기록
- `learned_habits`: 배우는 동물, 버릇, 가르친 동물과 획득 시각

첫 버전에는 배우는 동물·버릇별 활성 학습 상대가 한 마리뿐이다. 관련 추억
가구에서 두 소유자가 같은 게임 날짜에 각각 참여하면 그 날짜를 한 번
인정한다. 하루에 여러 친구와 활동해도 해당 학습의 일수는 하루만 증가한다.
서로 다른 3일을 채우면 버릇을 한 번 획득한다. 가르치는 동물의 소유자가
집을 나가면 미완료 학습을 종료하며 다른 동물과 새 학습을 시작할 수 있다.
완료된 버릇과 출처는 유지하고 같은 버릇을 다시 획득하지 않는다.

### 5.5 알림

- `notification_events`: 성공한 도메인 사건과 중복 방지 키
- `notification_deliveries`: 수신자별 대기·성공·재시도·실패 상태

추억 가구 완성은 현재 멤버이면서 viewer인 사용자, 버릇 습득은 배우는 동물과
가르친 동물의 소유자에게만 전달한다. 행위자는 같은 사건의 자기 알림에서
제외한다. Edge Function은 발송 직전 소속, viewer 권한, 알림 설정과 토큰
유효성을 다시 검사한다. 같은 추억의 연속 기여 알림은 사건 키와 시간 창으로
묶는다. 친구 입주 알림은 입주가 확정된 뒤 현재 활성 멤버에게 보내되 입주자
본인은 제외한다. 탈퇴자와 사건 접근 권한이 없는 신규 멤버에게는 알림 본문을
보내지 않는다. 영구 실패한 Expo 토큰은 비활성화한다.

## 6. 트랜잭션과 동시성

중요 RPC는 가능한 한 다음 잠금 순서를 사용한다.

1. `auth.uid()`에 대한 트랜잭션 advisory lock
2. 집 행 `FOR UPDATE` 잠금
3. 초대, 멤버십, 소유 아이템 또는 배치 행 잠금

집 생성은 사용자 잠금 후 집과 최초 멤버십을 생성한다. 초대 수락은 사용자
잠금 후 집을 잠그고, 사용자 활성 멤버십·초대 상태·만료·현재 인원을 같은
트랜잭션에서 다시 확인한다. 현재 3명인 집에 두 사용자가 동시에 수락하면
집 행 잠금 뒤 먼저 처리된 한 명만 성공한다. 한 사용자가 서로 다른 두 집을
동시에 수락하면 사용자 잠금과 활성 멤버십 고유 인덱스로 한 집만 성공한다.

동일 사용자의 동일 수락 멱등 키는 기존 결과를 반환하고 멤버십을 중복 생성하지
않는다. 한 명이 입주해도 4명 미만이면 초대는 유지한다. 4명이 되면 `full`로
종료한다. 이후 자리가 나도 되살리지 않는다. 초대 취소, 재발급, 집 보관과
정상 입주 이외의 인원 변동은 기존 초대를 종료한다.

탈퇴는 사용자와 집을 잠근 뒤 다음을 한 트랜잭션으로 처리한다.

- 탈퇴자 멤버십 종료
- 탈퇴자 소유 가구 배치 해제와 개인 보관함 회수
- 미완료 학습 상대 관계 종료
- 탈퇴자가 집장이면 `joined_at`, 멤버십 ID 오름차순으로 후임 결정
- 남은 활성 멤버가 없을 때만 집을 `archived`로 변경
- 기존 활성 초대 무효화

동물, 코인, 인벤토리와 습득한 버릇은 사용자에게 남는다.

출석 RPC는 사용자와 한국 날짜의 고유 제약으로 하루 100코인을 한 번만
지급한다. 집 이동은 추가 보상 사유가 아니다. 구매 RPC는 서버 카탈로그 가격을
읽고 잔액 차감과 아이템 지급을 함께 커밋하며, 멱등 키별 기존 결과를 반환한다.

가구 배치 RPC는 아이템 소유자, 활성 집 소속, 허용 슬롯, 슬롯 점유와 예상
배치 버전을 검사한다. 충돌 시 최신 배치와 명시적인 `placement_conflict` 오류를
반환한다. 다른 사용자의 소비성 간식은 사용할 수 없다.

## 7. 화면과 그래픽

### 7.1 내비게이션

- 인증 그룹: 로그인, 회원가입, 데모 진입
- 온보딩 그룹: 프로필, 동물 선택, 집 생성 또는 초대 입장
- 탭 그룹: 우리집, 꾸미기, 추억
- 상세 화면: 초대, 구성원, 상점, 인벤토리, 추억 상세·작성, 버릇 학습, 설정

딥 링크는 초대 토큰 또는 알림 사건 ID만 운반한다. 대상 화면은 항상 서버에서
현재 접근 가능 여부를 확인한다. 만료된 초대, 가득 찬 집, 권한이 사라진 추억은
서로 구분된 안내와 다음 행동을 제공한다.

### 7.2 공동 방

논리 기준 좌표는 `1000 x 1000`으로 두고 화면의 안전 영역 안에 종횡비를 유지해
확대·축소한다. 동물과 가구의 기준점은 발 또는 바닥 접점이다. 그 기준점의 y값을
기본 깊이로 사용하고, 고정 레이어와 안정적인 ID를 보조 정렬 기준으로 사용한다.

동물은 1~4마리 전용 앵커 세트를 사용한다. 네 마리일 때 각 이름표와 최소
44pt 상당의 터치 영역이 겹치지 않는다. 같은 종류를 여러 사용자가 선택할 수
있으며 이름표와 개인 포인트 색상으로 구별한다. `쉬는 중`, `놀고 있어요` 같은
동물 상태는 접속 상태와 분리하고, 실제 접속 여부를 암시하는 초록 점을 사용하지
않는다.

구성원 영역은 `현재 인원/4`와 네 자리를 표시한다. 빈 자리는 초대 진입점이며
초대 화면 열람은 자리를 예약하지 않는다. 초대 미리보기는 집 이름, 초대한 사람,
현재 인원만 보여주고 추억 글과 사진을 노출하지 않는다. 정원이 차면
`집이 꽉 찼어요`를 표시한다.

동물 상태 모델은 `idle`, `eating`, `resting`, `playing`, `reacting`이다. 행동
선택 규칙과 Reanimated/Skia 표현을 분리한다. 일상 애니메이션과 위치는 기기에서
재생하며 먹이, 배치, 버릇처럼 영속화할 사건만 서버에 기록한다. 줄어든 모션
설정에서는 큰 반복 움직임을 정적인 상태 변화로 대체한다.

### 7.3 꾸미기

첫 버전은 카테고리별 고정 슬롯에 아이템을 선택·교체한다. 드래그는 자유 좌표를
저장하지 않고 가장 가까운 호환 슬롯을 선택한다. 상세 패널에서 소유자를 표시한다.
집에 네 명의 가구가 있을 수 있도록 카테고리별 대체 슬롯과 개인 보관함을 제공하되
모든 소유 가구를 동시에 놓는 것을 목표로 하지 않는다.

텍스트 입력, 버튼과 터치 대상은 접근 가능한 역할·레이블·상태를 제공한다.
색상만으로 사용자나 상태를 구분하지 않는다.

## 8. 사진, Realtime과 푸시

추억 사진은 비공개 `memory-photos` 버킷에 사용자와 추억을 포함한 예측 불가능한
경로로 저장한다. 앱에서 허용 형식과 크기를 검사하고 압축한 뒤 업로드한다.
다운로드는 viewer 또는 탈퇴한 직접 기여자인지 서버가 확인한 후 제한 시간 URL을
발급한다. Storage 정책도 동일한 관계를 확인한다.

입력은 JPEG, PNG, HEIC/HEIF로 제한하고 원본 파일은 10MB 이하여야 한다. 앱은
긴 변을 최대 2048px로 줄이고 JPEG 품질 0.82로 압축하며, 업로드 결과가 5MB를
넘으면 사용자가 다시 선택하도록 안내한다. 원본 형식 메타데이터와 EXIF 위치
정보는 업로드 객체에 보존하지 않는다.

Realtime은 변경의 최종 내용을 운반하는 게임 상태가 아니라 재조회 신호다.
집 관련 테이블 사건을 받으면 관련 TanStack Query 키를 무효화한다. 재연결과 앱
활성화 시 전체 관련 쿼리를 다시 조회한다. 탈퇴·로그아웃 시 채널 구독과 이전 집
캐시를 제거한다.

Expo Notifications는 권한 요청, 토큰 등록, 포그라운드 수신과 알림 선택 라우팅을
담당한다. Edge Function은 대기 delivery를 Expo Push Service로 보내고 지수형
재시도, 영수증 확인, 중복 방지와 무효 토큰 정리를 수행한다. 푸시는 상태 저장이나
Realtime 대체 수단으로 사용하지 않는다.

## 9. 오류 처리

도메인 RPC는 앱이 분기할 수 있는 안정적인 오류 코드를 반환한다.

- `already_in_house`
- `house_full`
- `invite_expired`, `invite_revoked`, `invite_invalid`
- `not_house_member`, `not_house_admin`
- `memory_access_denied`
- `insufficient_coins`
- `placement_conflict`, `slot_occupied`
- `learning_partner_left`, `habit_already_learned`

사용자 화면에는 기술 오류 대신 해결 방법을 포함한 한국어 문구를 표시한다.
알 수 없는 네트워크 오류는 재시도를 제공하되 성공 여부가 불명확한 명령은 같은
멱등 키로 재시도한다.

## 10. 초기 데이터

SQL 시드는 40개 생활 아이템, 15개 추억 가구 외형, 기본 버릇 정의와 배치 슬롯을
생성한다. 앱 카탈로그는 DB 행의 ID와 에셋 키를 사용하며 가격과 지급 규칙은 DB를
최종 기준으로 삼는다. 에셋이 완성 일러스트로 교체되어도 정의 ID와 게임 규칙은
변경하지 않는다.

초기 그래픽은 자체 제작한 단순 도형과 로컬 에셋로 제공한다. 원격 이미지나 사용
권한이 불분명한 자료에 의존하지 않는다.

## 11. 테스트 전략

### 11.1 앱 테스트

- 데모 모드 표식과 Supabase 미설정 오류 상태
- 로그인 전 초대 보존과 로그인 후 재검증
- 1~4명 구성원 슬롯, `2/4` 표시와 빈자리 초대 동작
- 네 동물 이름표·터치 영역 계산과 동일 동물 구별
- 탭, 상점, 인벤토리, 추억 상세, 설정의 접근 가능한 동작
- Realtime 사건, 앱 활성화, 탈퇴·로그아웃 시 캐시와 구독 정리
- 예상 버전 충돌 후 최신 배치 표시

### 11.2 데이터베이스 테스트

- 사용자당 활성 집 하나와 집당 활성 초대 하나
- 하나의 초대로 세 명이 순서대로 입주
- 다섯 번째 입주 차단
- 마지막 자리 동시 요청에서 한 명만 성공
- 한 사용자의 두 집 동시 수락에서 한 집만 성공
- 동일 수락·구매·출석 요청 재시도의 멱등성
- 두 명의 기여로 가구 한 번 생성, 추가 두 기여에서 중복 미생성
- 후입주자의 과거 추억·사진 접근 차단
- 탈퇴자의 직접 기여 보관과 이후 타인 기여 접근 차단
- 집장 탈퇴 후 결정적인 승계와 한 명이 남은 집의 활성 상태
- 네 명의 가구 이동과 탈퇴 경쟁 후 소유·배치 일관성
- 같은 날 여러 친구 활동에도 학습 일수 한 번 증가
- 서로 다른 3일 뒤 한 번만 버릇 획득
- 구매 실패 시 차감과 지급 모두 롤백
- 한국 날짜 기준 출석 100코인 한 번 지급
- RLS 및 Storage 권한의 허용·거부 행렬

동시성 테스트는 서로 다른 데이터베이스 연결로 실제 경합을 일으킨다. 단일 세션의
순차 호출을 동시성 검증으로 보고하지 않는다.

### 11.3 모바일 확인

Expo 웹은 빠른 화면 검토에만 사용한다. Development Build에서 알림 권한·토큰,
초대 딥 링크, 앱 종료 후 재실행, 이미지 선택·압축·업로드를 확인한다. 외부 계정이나
실기기 없이 수행하지 못한 검증은 최종 보고에서 명시한다.

## 12. 빌드와 운영 문서

`eas.json`에는 development, preview, production 프로필을 둔다. README는 다음을
설명한다.

- Node와 패키지 관리자 요구 버전
- 데모 모드 설치·실행·테스트 명령
- Supabase 프로젝트 환경 변수와 로컬 CLI 실행
- 마이그레이션, 시드, DB 타입 생성 명령
- 비공개 Storage 버킷과 정책 적용
- Expo 알림 자격 증명과 Edge Function 배포
- Development Build와 EAS 빌드 명령
- 실제 연동 여부와 데모 한계

앱 번들에는 publishable/anon key만 사용한다. service role key와 푸시 관련 비밀은
Supabase 또는 EAS 서버 환경에만 둔다.

## 13. 구현 단계와 완료 기준

구현은 작은 커밋으로 다음 순서를 따른다.

1. Expo TypeScript 기반, 품질 도구와 데모 실행 셸
2. 도메인 타입, 저장소 계약, 데모 데이터 계층
3. Expo Router 흐름과 주요 React Native 화면
4. Skia 방, 4마리 배치, Reanimated와 고정 슬롯 꾸미기
5. Supabase 기반 스키마, 카탈로그 시드와 생성 타입
6. 집·초대·탈퇴·승계 RPC와 RLS
7. 출석·구매·배치 RPC와 Realtime 갱신
8. 추억·사진 권한·가구 완성 RPC
9. 버릇 학습 RPC
10. 알림 큐, Expo 클라이언트와 Edge Function
11. DB·앱 회귀 테스트, EAS 설정과 운영 문서

각 단계는 해당 테스트, 타입 검사와 린트를 통과한 뒤 커밋한다. Supabase 프로젝트나
실기기 자격 증명이 필요한 항목은 설정과 코드를 제공하되 실제 연결 검증을 수행하지
않았다면 완료로 표시하지 않는다.

첫 버전 완료 조건은 데모 모드에서 핵심 화면과 흐름을 실행할 수 있고, 자동화된
앱 테스트가 통과하며, Supabase 로컬 환경에서 핵심 제약·RLS·RPC 테스트를 실행할
수 있고, 실제 외부 연동에 남은 절차가 README와 최종 보고에 정확히 구분되는 것이다.
