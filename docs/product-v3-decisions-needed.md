# 제품 v3 — 승인 대기 결정과 기존 데이터 보호

작성: 2026-10-17 · 상태: **모든 V3-D 항목은 제안/승인 대기**

이 문서를 작성하거나 PR에 병합하는 행위는 경제·소유권 변경이나 운영 DB 적용 승인이 아니다.
현재 기준은 [product-spec](product-spec.md) 및 실제 main 계약이며,
[경험 제안](product-v3-proposal.md)의 재미 목표를 이유로 자산을 임의로 바꾸지 않는다.

## 승인 단위와 공통 절차

정책 승인, migration 코드 검토/병합, 격리 검증, 운영 DB 적용, 앱 배포를 분리한다.
과거 특정 조회 함수·기본 가구 지급의 승인은 이번의 전면 공용 전환·재화 폐지 승인으로 확대하지 않는다.
승인 기록에는 결정 ID, 선택한 대안, 대상 데이터/환경, 보상·예외·일정, 승인자·근거 링크를 남긴다.
아래 ‘제거’는 기존 사용자의 데이터를 즉시 지우라는 뜻이 아니다.

1. 별도 승인 범위에서 기존 건수·원장·소유 관계·실행 중 요청을 **읽기 전용**으로 조사한다.
   이 문서 작업에서는 운영 DB 조회·쓰기 및 계정/자산 조작을 하지 않았다.
2. 기존 필드와 RPC 호출자가 남는 기간을 정의하고, 추가 전용 migration·feature gate·호환성 계획을 검토한다.
3. 격리 DB 사본/합성 fixture로 정상·실패·중단/재개·반복 실행·다계정·퇴장 경합을 재현한다.
4. 변경 전 자산 합계/소유자/원본 출처와 변경 후 불변량을 대조한다. 승인된 가역 사본/원장을 만든다.
5. 운영 적용은 별도 승인과 복구 가능한 백업·점검 시간·담당자·중단 기준을 확보한 뒤에만 한다.
   기존 migration을 수정/삭제하지 않고, 불일치 시 쓰기 차단 후 forward fix한다.
6. rollback이 이미 발생한 사용자 행동을 되돌릴 수 없는 경우를 명시한다. UI gate 되돌리기와
   DB 역이관은 같은 작업이 아니다. 무승인 환불·삭제·legacy 보안 우회는 금지한다.

## V3-D01. 코인·출석·상점의 역할 축소 또는 제거

**현행/근거:** 기존 #151. 현행 개인 지갑·원장·KST 하루100코인·멱등 구매 유지. main의 coinBalance=0은 연동 결함 후보이지 폐지된 경제의 증거가 아니다.

### 기존 사용자 영향

잔액·수령 이력·구매 원장·보유 가구가 있다. UI만 없애도 구매 수단·수령 기대를 잃으므로 데이터 보존만으로 영향이 없다고 하지 않는다.

### 새 정책과 대안

권고: 우선 코인/수령/상점을 보조 경로로 유지하고 첫 꾸미기가 구매에 막히지 않는 별도 체험을 검증한다. 대안은 잔액 조회 전용 동결→판매 종료의 단계 전환. 완전 삭제·환율/보상은 승인 전 선택하지 않는다.

### 마이그레이션

단계적 전환안: 신규 판매·출석 쓰기 gate, 진행 중 request의 멱등 결과 조회 유지, wallet/ledger/reward/purchase/owned_items 보존. 기존 가격을0으로 덮거나 소급 지급하지 않는다. 구매·수령을 중단할 날짜와 이미 시작한 요청 처리 기준을 사전 고지한다.

### 되돌리기

UI/쓰기 gate 복구 후 동일 원장·잔액으로 재개. 조회 전용 기간 새 결과가 생겼다면 중복 차감/지급 검사 후 재개. 기록 삭제를 복구 수단으로 사용하지 않는다.

### 테스트

전환 전후 잔액·보유 수량 일치, 일일 중복 수령/중복 구매0, 응답 유실 재시도1결과, 구클라이언트 요청·퇴장 경합, 이전/새 계정 UI 접근 및 부족금액 검증.

### 승인 조건

유지/동결/폐지 선택, 잔액 사용·보상·고지 기간, 구클라이언트 호환 종료, 운영 적용·배포 승인 필요. #151은 승인과 실검증 전 닫지 않는다.

## V3-D02. 35종 기본 장식 무료 이용

**현행/근거:** 기존 #159. 카탈로그 상점40종 중 비소비 장식35종이라는 분류이며 전부 이미 공용 자산이라는 뜻이 아니다. 로컬 claimFreeFurniture는 개인 소유 지급이다.

### 새 정책과 대안

권고 검증안: 개인 무료 이용과 집 공용 라이브러리를 비교하되 혼자 시작의 첫 배치까지 완결되는 최소 범위를 먼저 평가한다. 무료 지급과 공용 소유 전환을 한 결정으로 묶지 않는다. 기존 구매품은 개인 자산으로 보존한다.

### 마이그레이션

승인 전 실행0. 개인 지급이면 definition별 idempotent entitlement와 기존 보유 탐지·중복 지급 정책 필요. 공용이면 house-scoped entitlement/placement 및 개인 item 출처를 분리하는 추가 모델이 필요. 35개를 owned_items 전 계정에 무조건 삽입하지 않는다.

### 되돌리기

신규 무료 지급 gate 중지, 이미 승인 지급된 자산 보존. 공용 라이브러리 중단 시 마지막 배치와 개인 가구 복구를 journal로 검증하며 임의 회수하지 않는다.

### 테스트

무보유 신규 계정 첫 배치, 기존 구매자·중복 보유자·4인·타인 자산, 재시도 중복0, 퇴장/집 변경/마지막 archive, 35종 호환 슬롯·로딩·offline 검증.

### 승인 조건

개인/집공용 모델, 대상35개 실제 definition 목록, 중복 보유·기구매자 보상 여부, 퇴장 시 처리와 적용 시점 승인. D05와 별개 승인 기록을 남긴다.

## V3-D03. 구매 간식 중단과 무료 교감의 관계

**현행/근거:** #151의 소비품 하위 결정. main의 간식 행동 RPC는 소비품 수량을 차감하는 계약이 아니다. 로컬 맥락 반응도 소비 증거가 아니다.

### 기존 사용자 영향

구매 간식의 수량·가격·미확정 구매 요청을 보존해야 한다. 소급 소비나 숨김은 사용 가치 상실을 만든다.

### 새 정책과 대안

권고: C02 무료 시각 교감은 기존 소비품과 분리. 간식 판매 중단/보유품 보관/선택적 꾸미기 기념품 전환/환불은 각각 대안이며 아직 미승인이다. 먹이는 의무·허기 페널티나 새 성장 수치를 추가하지 않는다.

### 마이그레이션

판매 gate와 보유품 노출을 분리. 전환 승인 시 원래 owned_item ID·수량·구매 출처를 journal로 연결하고 멱등 처리. 빈 상태로 가장해 기존 간식을 숨기거나 수량0으로 만들지 않는다.

### 되돌리기

판매 gate는 복구 가능. 전환된 기념품을 이미 배치/사용한 경우 역전환 충돌 계획이 있어야 한다. 무승인 회수·환불 재차감 금지.

### 테스트

행동 버튼만 눌러 수량이 줄지 않음, 보유/판매 종료 안내 구분, 구매 응답 유실·전환 반복·일부 실패 후 원래 수량/새 entitlement 불변량, 타인 간식 사용 거부.

### 승인 조건

판매 유지/중단, 보유품의 구체적 용도·전환/환불·가격 기준·고지, 원장 보존 기간과 운영 적용 승인 필요.

## V3-D05. 개인 가구를 공용 가구로 전환할지

**현행/근거:** 현행 구매·무료 개인 지급·author 소유 추억 가구는 모두 소유자 ID를 갖는다. 공용 슬롯 교체 권한과 자산의 공용 소유권은 별개다.

### 기존 사용자 영향

퇴장 시 회수·집 이동·본인만 이동/회수·구매 출처가 달라진다. 공동 추억의 의미도 author의 소유권 자동 박탈 근거가 되지 않는다.

### 새 정책과 대안

권고: 기존 개인 소유 유지, 필요하면 신규 house entitlement만 별도로 도입한다. 기존 가구의 profile_id를 house/admin/공용계정으로 바꾸는 일괄 전환은 하지 않는다. 추억 원본 viewer 권한은 공용 모델에서도 유지한다.

### 마이그레이션

개인 item과 집 entitlement를 다른 명령/타입으로 분리하는 추가 모델 제안. 출처·기존 배치·중복 관계·떠난 사용자 보관함을 연결하는 설계가 승인되어야 함. 기존 owned_items UPDATE 일괄 변환 금지.

### 되돌리기

신규 공용 기능 gate를 끄되 기존 개인 item은 영향 없음. 승인 전환이 있었다면 원래 owner/quantity/placement journal로 복구 가능성을 검증하고, 타인 편집은 임의 소거하지 않는다.

### 테스트

A/B교체 시 수량불변, 타인ID 이동/회수 거부, 개인/공용 동일외형 구분, 퇴장/승계/집archive, 추억viewer후입주·cutoff·원본 삭제, 네트워크재시도.

### 승인 조건

누가 공용 항목을 편집/제거하는지, anti-griefing·undo, 퇴장·집archive의 귀속, 기존 개인가구 전환 옵트인·복구 및 별도 개인정보 검토 승인 필요.

## V3-D06. DB 구조 정리·migration 폐기

**현행/근거:** 현행은 추가 전용 migration·원장·고유 제약·RLS·실행 권한을 유지한다. 문서 정합화는 schema 삭제 프로젝트가 아니다.

### 기존 사용자 영향

과거 이름·관계·RPC 호출자·자산/추억 FK·감사 이력과 복구 가능성이 영향을 받는다. 기존 파일 변경은 신규환경과 운영 적용 이력을 갈라놓는다.

### 새 정책과 대안

권고: 삭제 없이 확장→클라이언트 전환→측정→별도 승인 후 정리. 필요 없는 UI 경로 비활성화와 DB 물리 삭제를 분리한다. migration squash·기존 이력 삭제는 이번 범위에서 제안 실행하지 않는다.

### 마이그레이션

새 파일만, 권한 revoke와 구RPC 우회 차단 포함. no-seed/seeded reset, history 정합성, 새/구클라이언트·backfill멱등성·실패 rollback을 검증한다. 사용하지 않는 것처럼 보이는 table도 운영 의존성 확인 전 DROP 금지.

### 되돌리기

계약 버전별 UI/API gate 차단과 forward fix 우선. 보안상 금지된 unscoped RPC를 되살리지 않는다. 데이터 restore는 백업시각 이후 타인활동 손실을 포함해 별도 복구 승인 필요.

### 테스트

새DB 전체적용·기존DB upgrade·no-seed카탈로그·RLS/GRANT/SECURITY DEFINER·구RPC직접호출·부분실패·동시성·자산FK·백업복구훈련.

### 승인 조건

schema별사용자영향·개인정보보관정책·호환종료·백업/복구계획 검토, 운영적용과 배포 별도승인. 과거 migration 파일 삭제는 안전하다는 추정만으로 허용하지 않는다.
